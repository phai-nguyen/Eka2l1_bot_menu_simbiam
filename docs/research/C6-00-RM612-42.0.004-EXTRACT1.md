## PhoneUIUtils exact-binary caveat

C6 phoneuiutils.dll E32 metadata:
- UID1: 0x10000079
- UID2: 0x1000008D
- UID3: 0x101F4D0F
- CPU: ARMv5
- compression: Symbian byte-pair
- code size: 0x67DC
- text size: 0x67DC
- code base: 0x8000
- export count: 462

The public SymbianSource phoneuiutils EABI DEF contains only 387 exports.

Public SymbianSource labels:
- ordinal 181: CPhoneMainResourceResolver::Instance
- ordinal 182: CPhoneResourceResolverBase::BaseConstructL
- ordinal 307: CPhoneResourceResolverBase::ResolveResourceID
- ordinal 308: CPhoneResourceResolverBase::IsTelephonyFeatureSupported

Because the production C6 binary has 462 exports versus 387 in that public
DEF, ordinal->symbol mapping is NOT portable between these builds.

This changes the interpretation discipline for NATIVEBOOT2:

B77 proved that RM-356 runtime ordinal 182 resolves to a concrete address
(+0x1BC8 in that loaded binary), but the name BaseConstructL came from the
public SymbianSource DEF rather than an exact RM-356 symbol artifact.

Therefore:
- keep B77's exact runtime address/export evidence;
- downgrade the symbol label "ordinal 182 = BaseConstructL" to an
  UNVERIFIED SYMBOL HYPOTHESIS until the exact RM-356 phoneuiutils.dll is
  inspected;
- do not implement a functional B80 fix by hooking ordinal 182 solely because
  the public DEF names it BaseConstructL.

This is the most important safety result from the C6 control image so far.
